# 工作台实际使用链路验收

## 目标与边界

本轮验证现有工作台的发送、工具执行、明确答复、连续追问、停止和历史回放，不新增产品能力，不调整 Pi 压缩策略。发现缺陷后先保存复现证据，再作针对性修复。

使用隔离工作区、独立端口和 SQLite，不修改日常数据及仓库模型配置。真实模型使用当前默认服务；历史凭据仅在用户已授权范围内提取至临时配置，结束清理。模拟模型回归与真实模型结果分开记录，不用占位响应作为远程验收。

## 流程与判定

| 节点 | 操作 | 必须取得的证据 |
| :--- | :--- | :--- |
| 1 | 浏览器创建 Task，要求读取测试文件 | UI 创建的 Run/Turn、真实远程抓包、完成的文件读取工具、包含随机文件标记与金额的明确答复 |
| 2 | 同一 Task 继续追问 | 新请求包含上轮文件证据；答复标记与计算正确，不重复读取文件 |
| 3 | 要求执行隔离的 30 秒命令 | 本地脚本已启动的标记及 PID、ToolCall、运行中界面；不把模型口头声明当执行 |
| 4 | 命令运行中刷新，再点击停止 | 刷新没有新增 Run；停止 HTTP 响应、Run/Turn 的 interrupted 状态、子进程退出、发送入口恢复 |
| 5 | 停止后继续提问 | 同一 Task 可创建新 Turn，仍能使用已取得的文件事实；停止的命令不重放 |
| 6 | 刷新，再关闭服务并重建 Session 查看历史 | 原问答完整可见；历史 Session 只读；Run、工具及抓包数量不因回放增加 |

流程：`浏览器发送 → LocalApi → RunCoordinator → AgentKernel → AgentLoop → Tool/LLM → SQLite/SSE → 浏览器`。每步关联原始 ID，报告计时为本机墙钟，不宣称速度或成本优化。

## 执行与放行

- 现有回归：`npm --prefix code run web:build`、`npm --prefix code run web:test:e2e`。
- 真实链路：在 `code/` 执行 `npx tsx e2e/workbench-real.pw.ts`；默认读取当前配置。仓库配置密钥为空时，不允许以占位响应放行。
- 已授权的历史凭据验收可显式设置 `FIGO_ACCEPTANCE_KEY_COMMIT`；只接受与当前 Provider ID、模型和端点一致的历史条目，不将历史配置整体恢复到工作区。
- 每次输出独立 `.figo-agent/acceptance/workbench-flow-<时间>/`，保存 JSON 报告、截图与工作区 SQLite；步骤结果同步记录为 `WorkbenchFlowAcceptance` 事件。
- 必需节点失败则本链路不放行；远程超时、页面错误和证据不足分别如实记录，不反复挑选成功结果覆盖原失败。
- 本轮不验证真实大窗口压缩、三模型横向性能、桌面安装包、异常强杀恢复及审批流程。

### 发现并修复的问题

1. **服务关闭期间接受 SSE 重连，导致退出不结束。** `local-api.ts` 原先结束已有连接后，再等待 `coordinator.waitForIdle()`，期间新连接仍返回 200 并保持打开。新增测试固定住这个间隙，修复前断言得到 `200 != 503`；修复后在关闭入口同步设定关闭标志，新请求返回带 `Connection: close` 的 503，重复关闭复用同一 Promise。Host/Origin 检查仍在关闭判断之前。
   复核还发现关闭前已经接收请求头、正文未收全的 Run 提交会越过入口检查。真实 HTTP `Expect: 100-continue` 用例先确认 `202 != 503`，再在读取正文和文件引用之后、同步提交 Run 之前复核关闭状态；现在拒绝该请求且 `ui_runs=0`。不以新 GET 的拒绝代替半截 POST 的验收。
2. **已取消命令误记完成。** `runShellCommand()` 被取消后会返回已结束进程的信息，`run_command` 原先无条件包装为 `completed`，截图中工具显示“完成”。新增测试在修复前得到 `status=completed, exitCode=null`；修复后在命令返回时复核 AbortSignal，经现有 ToolRegistry 错误路径留痕，不再发布工具完成事件。正常命令、终端适配及 Pi 算法不改。
3. **文本协议未发送工具参数契约。** 实测 `read_file({file:"order.json"})` 失败后模型绕到 `read_many_files`；原始抓包只有名称与描述，没有 `path` 参数定义。为 `read_file` 声明现有 `inputSchema` 并明确校验非空字符串 `path`，错误返回 `invalid_input`；消息构造器按已有契约仅向文本提示加入 schema，原生 Provider 仍通过既有 `parameters` 发送，不重复塞进 system。参数错误、schema 声明及文本发送三项测试均先红后绿，关联原生错误结果测试同步更新错误码，保留失败与调用 ID 配对断言。

产品修改限定为 `local-api.ts`、`command-tools.ts`、`read-only-tools.ts`、`llm-message-builder.ts` 以及中文资源和对应类型；其他新增内容为验收脚本、测试和文档。只补实测涉及的 `read_file` schema，不扩展其他工具目录或引入全局 schema 验证器。四个 Pi 核心文件 SHA256 与此前验收一致。

## 经验提炼

- 停止必须分别核对 UI 状态、持久化状态和实际子进程；按钮变回“发送”不足以证明停止成功。
- 关闭服务时要先停止接收新工作，再结束现有长连接；只清理一次连接集合不能覆盖重连间隙。
- 异步读取正文和引用期间，服务状态会变化；执行准入必须在真正提交 Run 前重新检查，不能只检查 HTTP 入口。
- 工具名称和描述不能替代参数契约；参数缺失应指出缺少哪个字段，不能等待读取根目录后只返回系统错误。
- 连续追问的证据链应同时验证“新请求携带旧事实”和“新答案使用旧事实”，不能仅看到界面有历史文本就宣布上下文正确。
- 保存失败验收器和真实缺陷记录，区分测试错误、产品缺陷和远程服务行为，避免把重跑成功当成失败从未发生。
