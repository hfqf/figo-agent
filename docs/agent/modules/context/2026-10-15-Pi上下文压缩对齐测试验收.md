## 四、三模型真实验收

必须使用当前本机启用的模型条目。模型 ID、地址、实际窗口、最大输出和来源写入单独结果记录；记录不得包含密钥。中转能力未知时保持未核实，不自动复制官方值。

每个模型按同一真实任务前缀建立自己的历史快照；模型间结果分开对照，不把不同模型生成的历史当成完全相同输入。每个模型完成：

1. **默认值长任务**：W 使用核实后的端点值，R=16384，K=20000；记录自然运行是否到达阈值。没到阈值就写未触发，不下调参数冒充自然触发。
2. **机制触发**：在独立测试配置中显式缩小 W，使用真实历史触发自动压缩。记录“测试窗口”与“真实窗口”，单次输入无法装下时先构造合法多轮前缀。
3. **手动与后续**：执行手动压缩，然后要求完成真实工具任务与复述预先定义的关键事实；检查下一次请求确实使用新条目和保留原文。

| 关键节点 | 每个模型必须给出的具体数据 |
| :--- | :--- |
| 参数 | Provider、Model、端点、W、maxTokens、来源、R、K、是否测试覆盖 |
| 压缩判断 | 对应 requestId、usage 或估算方式、tokensBefore、阈值 W-R、触发原因 |
| 切点 | 首个保留 sourceRef、参与摘要的来源范围、近期原文估算量、工具配对检查 |
| 摘要请求 | purpose、HTTP 状态、实际输出参数、输入/输出 usage、耗时；缺失值写未知 |
| 保存与重建 | 压缩条目 ID、base ID、数据库写入结果、实际下一次请求及其完整抓包引用 |
| 后续质量 | 已完成/未完成目标、必须保留的事实、实际工具行为、错误与重读次数 |
| 对照收益 | 同模型同历史下关闭/开启分支的摘要次数、后续调用次数、完整 Turn 耗时、实际请求大小和报告用量 |

摘要 HTTP 成功只算调用成功；新条目保存、进入后续请求和后续任务完成分别给结论。输入缩短不等于净成本降低；输入计费、缓存口径或服务端用量异常必须单列。单任务检查只能支持该任务的结果，不能声称所有任务质量无损。

## 六、2026-10-15 实施留痕

### 实际范围与职责

- `pi-compaction.ts`：移植固定 Pi 纯算法；`compaction-preparation.ts`：宿主消息、有效 usage 与 omitted 后缀适配。
- `pi-summary.ts`：同模型生成普通/分割前缀摘要、滚动更新、文件操作合并；提示与错误文案在专属中文 JSON。
- `context_messages`：稳定来源主键的精确追加消息、反馈、合成失败结果与 usage 作用域；省略只标记 `omitted`。保留原文，不用脱敏 Trace 回放模型输入。
- `context_compactions`：事务追加摘要、保留边界、覆盖来源、base、请求及文件元数据；旧 JSON 表只读兼容。
- Loop/Kernel：两个正常检查点、`/compact [关注点]`、一次恢复、文本/原生截断工具均不执行；流式废弃尝试重置通过 SSE 实时与重放生效。
- 工作台只增加消息级压缩边界兼容与流式 reset，不新增调参、质量评分或优化调度页面。

快照表是复核后补充的宿主适配。实测旧反推路径的双工具批次运行合计 **12000 字符**，逐项默认重建为 **16254 字符**；反馈保留后立即取消则没有下一抓包，边界无法重建。精确快照使保留边界在摘要提交前已经可独立读取，避免靠推断补造历史。旧数据缺少自定义预览预算或已被删除的反馈时，仍属于明确兼容限制，不伪造缺失数据。
