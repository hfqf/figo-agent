## 2. 总体判断

**当前项目是一个本地优先的模块化单体 Agent Harness，采用单智能体 ReAct 式工具循环，以静态能力注册组织扩展，以工作区 SQLite 保存运行事实，通过 CLI、Web 和 Electron 暴露交互入口。**

这不是纯聊天应用，也不是多智能体平台、独立 Plan-and-Execute 引擎或完整事件溯源系统。模型决定下一步动作，AgentLoop 负责流程控制，Policy 决定模型动作是否获准执行。

现有运行主干应保留。需要改进的是边界的一致性与使用链路，而不是重新搭建一套架构。

## 5. AgentLoop 的实际机制

1. Kernel 将 Task、Turn、工作区和当前模型传给 Loop。
2. ContextBuilder 生成 ContextPack，显式 Skill 才运行本地预检；预检不是最终答案。
3. Loop 读取当前 Task 的消息投影、提示词和模型元数据。启用压缩服务时，不把 ContextPack 中的历史再重复拼入消息，而是重建有效消息序列。
4. 追加本次用户输入前检查历史压缩；需要继续工具循环时，再检查一次。
5. `for (let round = 0; ; round++)` 请求模型，没有固定总轮数上限。
6. 原生工具调用与文本工具协议分开解释。无效协议先限次修复，本次不执行工具；截断工具调用补失败结果再继续调度。
7. 合法工具动作交给 Runtime / Registry / Policy。批次结果按照单项预览与整批预算进入下一次请求，原始事实与消息快照分别保存。
8. 返回正文且没有工具动作时，生成最终答复与报告；格式修复耗尽、重复无新增超限或恢复失败进入失败终态。Web 停止通过 AbortSignal 进入 interrupted。

关键限制：无进展检测依据工具结果的指纹，不是任务目标完成度判断；“工具结果有新内容”与“正在接近用户目标”不是同一事实。当前没有额外的目标验收模型。

直接证据：`agent-loop.ts:238`、`:318`、`:353`、`:379`、`:425`、`:453`、`:465`；`run-coordinator.ts:143`、`:193`。

## 6. 上下文和记忆

### 6.1 四种记录不能混淆

- ContextPack：本轮准备了什么，记录条目、来源和纳入原因。
- Conversation Projection：本次执行有效的摘要与原始消息序列。
- HTTP Capture：某一次请求实际传输的请求体、响应体与状态。
- Memory：从 SQLite `memory_records` 按 scope 读取的相对稳定信息，不等于压缩摘要。

`ContextPack.estimatedTokens` 使用条目字符估算；压缩判断通过消息级 Pi 估算，结合匹配 usageScope 的历史实际 usage。两者不是同一个计算口径。实际请求以抓包为准。

### 6.2 压缩的分工已经明确

自动条件为 `enabled && contextTokens > contextWindow - reserveTokens`，窗口未知时跳过自动压缩。默认预留 16384 Token，近期原文保留目标 20000 Token，可按 Provider / Model 在 JSON 覆盖。

本地代码负责估算、触发、切点和来源维护；大模型负责把历史前缀与旧摘要合成新 Markdown 摘要。新条目保存摘要、保留边界和来源，不删除消息原文。超限恢复允许一次压缩后重试，失败不会伪装成成功。

这轮分析不调整 Pi 算法，不新增阈值自优化，不声称省钱、提速或语义质量提升。上述收益需要配对任务与实际用量、质量证据，不能由架构图推出。

直接证据：`compaction-policy.ts:9`、`pi-compaction.ts:142`、`compaction-preparation.ts:35`、`pi-summary.ts:47`、`compaction-service.ts:128`。

### 6.3 Memory 仍是基础实现

`SqliteMemoryStore.search(scopes)` 只按 scope 过滤并按更新时间排序，没有 query 相关性排序、向量召回或自动学习。ContextBuilder 读取 project / user 两类记录；数据仍位于工作区数据库，因此 `scope=user` 这个标签本身不提供跨工作区共享。

这属于明确的当前能力边界，不应在介绍中写成已经实现完整长期记忆系统。

## 7. 已成立的优点

1. **工具动作和权限分离。** 模型输出不直接执行，Registry 在执行前调用 Policy。
2. **一个内核、多种入口。** Electron 复用 Web 与本地服务，不复制 AgentLoop。
3. **历史和派生结果分离。** 原文、摘要边界、抓包、Trace、Usage 能以 ID 关联，而非只剩最终回答。
4. **正常多轮和异常边界分开。** 不用固定轮数截断正常调查，针对协议错误、容量错误和重复无新增分别处理。
5. **Inspector 以事实读取为主。** 它组合多表结果，不能反向变成上下文或运行状态源。

观测写入不是完全独立的旁路：Loop 多处等待 `trace.record()`，Recorder 先同步写 SQLite，再等待 JSONL 追加。它当前处于执行关键路径，不能把这套结构介绍成异步遥测；没有性能测量，本次不对其快慢下结论。直接证据：`code/src/trace/trace-recorder.ts:44`、`:68`。

## 9. SOLID 视角

- **S：部分成立。** Storage、Policy、Provider、Usage 有独立职责；Loop、API 与大页面仍承担多种变化原因。
- **O：工具扩展优于 Skill 扩展。** 工具有注册与执行边界；新增具体 Skill 仍需要调整 Loop 的固定获取和编排。
- **L：本次未做完整替换性验证。** 静态类型存在不证明所有 Provider 的错误、流式与工具行为等价，不能宣称已全面满足。
- **I：部分成立。** 有 LLMProvider / Policy / ToolExecutor 等较小契约；Context、Skill、Reporter 的使用端还依赖具体实现。
- **D：部分成立。** Provider 与工具通过接口和注册获取；Kernel 到 UI 租约的依赖、Loop 对具体 Skill 的依赖需要收敛。

结论是“现有架构已形成可用主干，但小内核和插件边界尚未贯彻到底”，而不是“所有模块已经完全低耦合”。

## 11. 经验提炼

1. 架构设计图应区分“控制权、事实记录、展示投影”，否则上下文、Trace 与抓包会被混为一谈。
2. “静态插件容器”不是“一切皆插件已完成”；真正的可替换性要检查调用端是否仍依赖具体实现。
3. “本地能用”与“多租户安全”是两种边界，Shell cwd 检查不能替代操作系统隔离。
4. 刷新历史列表消失是视图恢复问题，应从视图状态修复，不能通过新建或搬迁 Task 来掩盖。
5. 实验项目的下一步应选择可验收的小改动，先解决已复现的使用问题，再按触达范围整理模块。
